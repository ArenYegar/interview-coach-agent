# 工程复盘：这个项目踩过的坑与修法（面试可讲版）

> 用途：项目复习 + 面试应对。每条都按同一个骨架写：**现象 → 怎么复现 → 根因 → 怎么修 → 怎么验证 → 面试怎么讲**。
> 所有结论都有实测证据（命令 + 数字或产物文件路径），不是"应该没问题"。
> 记录时间：2026-09-20 ｜ 对应提交前状态：81 项单测全过

---

## 0. 三条主线（面试被问"你这个项目最难的地方是什么"，可以按这三条讲）

1. **"可复现"和"不枯燥"是一对矛盾，要分场景取舍。**
   评测要可复现（同输入必须同输出，否则分数不可比），练习要多样性（每次同一套题等于背题）。
   我的做法是把两者做成开关：评测口径下确定性选题；练习模式默认"换一套题 + 避开最近 3 场做过的题"，
   同时留一个随机种子，需要复现时把种子固定下来即可。
2. **"覆盖岗位要求"和"看起来像目标岗位的题"是两件事，必须同时满足。**
   只追求覆盖，就会把 JD 里"熟悉 Python"这条要求对应成 Python GIL / Docker 瘦身这类后端基础题，
   用户会觉得"我不是在练 AI 岗"；只追求方向，又会出现"题目很 AI、但没考到岗位真正要求的点"。
   我的做法是：覆盖第一优先，同时给方向类目加权、并给非方向类目设配额上限，两条都要守住。
3. **错误必须显式暴露，不能伪装成成功。** 本项目最危险的几类 bug 都是"看起来一切正常"：
   评测脚本把上一次的有效结果覆盖成空值、依赖缺失被写成"格式不支持"、模型返回空内容被当成"解析失败"。
   凡是这类地方，现在都改成"要么给出真实原因，要么宁可不写"。

## 1. 追问会重复同一个问题（用户实测发现）

- **现象**：连续两次答不出某道题时，系统追两次问，第二次的问题和第一次**一模一样**，等于把人卡死在原地。
- **复现**：用同一道题连续回答"不会"，看两次追问的文案——实测两次都是
  「你在「覆盖度」上少讲了：CPU密集、IO密集、多进程。请补充具体做法、取舍和结果。」（逐字相同）
- **根因**：追问文案是"按当前这道题最低分维度 + 还没命中的要点"现算的。
  两次回答都是"不会"，评分结果没变化，于是输入没变、输出自然一模一样；
  代码里**没有记录"上一次已经问过哪些要点"**，也没有换维度。
- **怎么修**（两条一起才有效）：
  1. 记录已问要点：每次追问都记下"这层问了哪几个要点"（会话状态里落盘，刷新也不丢）；
  2. 换维度 + 只问新的：第二层追问自动换一个维度问，并且只挑"还没问过"的要点；
     **如果已经没有新要点可问，就直接停止追问**——宁可少问一层，也不重复同一个问题。
- **验证**：同一场景重跑，两次追问变成
  「覆盖度：CPU密集、IO密集、多进程」→「换个角度：「深度与取舍」里的 实测 还没落到具体做法上」；
  单测里另有 3 条断言：两层的文案必须不同、两层问的要点集合不能重叠、要点问完必须返回"停止"。
- **面试怎么讲**：*"追问的价值在于'问出新的信息'，如果第二层和第一层问同一件事，用户除了重复一遍什么都做不了。
  所以我给追问加了状态：记住问过什么、第二层换维度问、没新东西可问就停。"
  "这里有个取舍：我限制了每题最多 2 层追问——层数太多会变成审讯，2 层足够把'没讲清'的地方逼出来。"*

## 2. 每次生成的题目完全一样（用户实测发现）

- **现象**："每次生成的题目好像是一样的"。
- **复现**：同一份 JD + 简历，连续出题 3 次，题号列表完全相同（实测：三次都是同一组，一字不差）。
- **根因**：选题是"打分 → 按分数排序 → 取第一名"，而且题目 id 参与了排序，所以是**完全确定性**的。
  这在评测里是优点（同输入同输出、分数可比），在练习里是缺点（等于背题）。
- **怎么修**：把"确定性"变成可选策略，练习模式默认开启多样性：
  - **避开最近做过的题**：读本地历史库，把最近 3 场出过的题排除在候选之外（有替代题时才排除，保证覆盖不塌）；
  - **在前列候选里随机**：不总取第一名，而是在"相关性不低于最高分 85%"的前几名里随机挑一个；
  - **随机种子显式化**：需要复现时传入固定种子，同种子必然给出同一套题（评测/回归口径不变）。
- **验证**：多样模式连续 3 次给出不同组合；同种子两次完全一致、异种子不同；
  开启"避重复"后，最近场次做过的题不再出现。
  单测 4 条锁定：默认确定性、多样能变、同种子可复现、排除集生效。
- **面试怎么讲**：*"可复现和多样性是两个目标，我把它们做成开关而不是改默认行为：
  评测口径必须确定性，练习口径默认换题。随机也不是随便抽——只在分数接近的前列里抽，
  保证随机不降质；同时留 seed，任何人能把一次随机结果完整复现出来。"*

## 3. "题目偏向后端"——一半是真问题（口径需要说清）

- **现象**："我感觉题目偏向后端方向"。
- **实测结论：不是分类失衡，而是分类均衡里的一类题"观感偏后端"。**
  出题分布本身是均衡的：Agent / LLM 应用 / RAG / 项目深挖 / 技术基础 各 1 道；
  问题出在"技术基础"这一类里的题多是 Python GIL、FastAPI 依赖注入、Docker 镜像瘦身这类**后端工程题**，
  而它们是被 JD 里"熟悉 Python，具备项目开发与线上部署经验"这条**硬性要求**拉进来的——所以它其实答对了要求，
  只是看起来不像 AI 岗的题。
- **怎么修**（不是简单删题，而是"覆盖"和"观感"同时管）：
  1. 方向识别：JD 里出现大模型 / Agent / RAG / Prompt 等词时，判为 AI 应用方向；
  2. 方向加权：相关性相同时，方向类目的题优先（权重 ×1.25）；
  3. 配额上限：非方向类目（技术基础 / 算法模型 / 行为动机）合计不超过约 40%，k≥4 时每类最多 1 道；
  4. **覆盖优先级不动**：每条硬性要求仍然要有对口题——不能为了"躲后端"而答不对岗；
  5. 类别均衡也用到逐条要求阶段：避免 k 小的时候 5 道题里有 3 道都是同一个类目。
- **验证**：AI 应用 JD 下 k=5 的出题变为 Agent / LLM应用 / RAG / 项目深挖 各 1 + 技术基础 1，
  非方向题占比 ≤40%；非 AI 岗位（如 Java 后端）不会被套上方向配额（单测覆盖两个方向）。
- **面试怎么讲**：*"这个反馈有一半是错觉、一半是真问题。错觉是分布本来就均衡；
  真问题是'技术基础'这类题的观感——它们由 JD 的 Python 要求拉进来，答题方向没错，但看起来不对口。
  我的处理不是把这类题删掉（那会让覆盖率失真），而是给方向类目加权 + 给非方向类目设配额，
  同时保持'每条硬性要求都要有对口题'这条硬约束。"*

## 4. 评测脚本会"静默毁数据"

- **现象**：照文档跑一次评测，机器复核结果文件被写成 7 行空值，上一次的复核数据没了。
- **根因**：复核需要真实模型；那次运行环境里没有 API Key，7 次调用全部失败，
  但代码**无条件覆盖**结果文件——失败也要写，于是把有效数据冲掉了。
- **怎么修**：① 没有 Key 或处于离线模式时，直接标"复核不可用"并**不发起任何调用**；
  ② 一条有效配对都没产生时，**保留原文件不覆盖**，只汇报状态与首个失败原因；
  ③ 只有真的算出结果才写文件。另加 7 项单测锁住（用哨兵文件 + 内容校验比对）。
- **验证**：跑前跑后对文件做内容校验，确认完全一致；`git status` 里该文件不再出现；单测覆盖三条路径。
- **面试怎么讲**：*"这类 bug 最危险，因为它不报错。我的原则是：批处理脚本在没有凭证的环境里跑，
  宁可不写，也不能覆盖既有产物；失败要显式标状态，不能伪装成一次成功运行。"*

## 5. PDF 解析只认一个库，导致"明明能读的简历报缺依赖"

- **现象**：用户上传自己的 PDF 简历，界面直接报"缺少 PyMuPDF，请另存为 docx"。
- **复现**：本机环境里确实没有 PyMuPDF，但有 pypdf / pdfplumber / pdfminer.six——**PDF 本来是能读的**。
- **根因**：解析只走了一条路径，把"可选依赖"当成了必需依赖；错误信息也没告诉用户"还能怎么办"。
- **怎么修**：改成多后端依次回退（pypdf → pdfplumber → pdfminer.six → PyMuPDF），
  全部失败时把**每个后端各自的结果**（未安装 / 异常类型 / 取到 0 字）写进报错，并给出下一步（另存为 docx/txt）。
  另外补一条真实场景：图片版 PDF 只能取到零星文字，这时在正文末尾附一句提醒，不静默通过。
- **验证**：用真实 PDF 简历实测：1979 字符 / 46 行解析成功，并走 HTTP 接口完整跑通出题；
  另有一个"只有 61 字符的图片版 PDF"被正确提示。单测用自造的最小 PDF 覆盖回退链与失败信息。
- **面试怎么讲**：*"凡是'可选依赖'，代码必须能降级；而且报错要给出可执行的下一步——
  '缺少库'不是答案，'我试过这四个都失败了，你可以另存为 docx'才是。"*

## 6. 配置参数在 import 时被快照，`.env` 里一半设置静默失效

- **现象**：配置文件里写了"输出上限 2048"，程序实际一直用 900，**没有任何提示**。
- **根因**：这几个参数被写成了模块级常量（import 时求值），而 `.env` 是在 import 之后才加载的；
  偏偏同一份配置里"端点 / 模型链"写成了函数（每次调用现读），于是表现为**一半配置有效、一半无效**，
  极难察觉。
- **怎么修**：这些参数一律改成"每次调用现读"；同时让 `--env-file` 在**构造命令行解析器之前**预加载，
  否则"题目数量"这类参数的默认值仍是旧快照。
- **验证**：改配置后直接读参数即可看到新值（4 条单测：运行时读取生效、旧常量不再被误用、未设置时取默认值、
  预加载先于解析器默认值）。
- **面试怎么讲**：*"配置读取时机是个容易翻车的地方：模块级常量是 import 时快照，函数是调用时读取。
  同一个配置文件里两种混用，就会出现'一部分生效一部分不生效'。我统一成后者，并补了测试。"*

## 7. 测试自己写垃圾文件（工程卫生）

- **现象**：跑完单测，项目的结果目录里多出几个随机命名的报告文件。
- **根因**：测试里想替换掉被测的引擎对象，但替换的位置不对（被测模块是"从别处导入"再使用，
  要替换的是**它自己命名空间里的那个名字**），于是真跑了一场引擎并落盘。
- **怎么修**：替换到正确的命名空间；并在流程上定一条自查：跑完单测立刻看版本控制状态，
  出现随机命名的产物就说明这类替换漏了。
- **验证**：跑完 81 项单测后工作区只有预期的改动，没有多余文件。
- **面试怎么讲**：*"测试也必须讲卫生：测试会真跑业务逻辑、写真实文件、污染结果目录。
  我的检查方式很土但有效——跑完测试看 git status，多出来的文件就是漏改的地方。"*

## 8. 前端/交互层的四个坑（Web 界面）

1. **首屏空白**：为了让"恢复上次未答完的场次"直接进第 3 步，把第 1 步默认隐藏了，
   结果没有历史场次时没人负责把它显示出来，页面全白。修法：启动流程先尝试恢复，恢复失败才显示第 1 步。
2. **题号叠加**：追问题号在视图层又拼了一次后缀，出现"技术-01-F1-F2"这种畸形 id。
   修法：题号只在一处生成，视图层直接用传进来的那个。
3. **表格列被挤成竖排**（表头"得分"两行）：固定表格布局 + 给列指定宽度 + 关键列不换行。
4. **高分辨率屏下大片留白**（用户明确讨厌）：首页改成双栏——左边上传、右边"最近练过的几场 + 流程说明"；
   作答页在输入框下方补"本场已答记录"表。空白要用有用信息填，不是靠拉大间距。
- **面试怎么讲**：*"这四条都不是算法问题，但每一条都会让'能跑'变成'不想用'。
  我改完会用无头浏览器把首页、作答页、报告页各截一张图逐条核对，而不是凭感觉说没问题。"*

## 9. Web 路径的 trace 被清空 → 成本账显示 0（"看起来正常，实际没测到"）

- **现象**：CLI 跑一场能从 trace 算出 11 次调用 / 16,680 token；但 Web 界面跑完的报告里
  `cost.llm_calls = 0`、`total_tokens = 0`，`runs/<id>/trace.jsonl` 只剩 1 行（`state.aggregate`）。
- **复现**：建会话 → 作答 → finish → 看 `runs/<id>/trace.jsonl` 的行数与报告里的 `cost`。
- **根因（两层叠加）**：
  1. `Tracer.__init__` 原先无条件 `write_text("")` 清空 trace，而 Web 界面是**每个 HTTP 请求新建一个引擎**
     （会话状态走 `web_state.json`，引擎不常驻）⇒ 每次请求都把上一步的 trace 清掉；
  2. 成本汇总原先只读**进程内计数器**（`Tracer.summary()`）⇒ 跨请求自然读不到。
- **修法**：
  1. `Tracer(..., append=False)` 新增参数；恢复已有会话时传 `append=True`
     （`WebSession.load` → `CoachEngine(trace_append=True)`），CLI 新建 run 仍然清空（复用 run_id 不会混进旧事件）；
  2. 新增 `trace.cost_summary(run_id)`：**只读 trace 文件**算成本，键与 `Tracer.summary()` 对齐，
     并带 `source` 字段（`tracer-memory` / `trace-file`）标明数字出处；
  3. `WebSession.finish()` 用文件口径写入 `report.cost`。
- **验证**：同一场 Web 会话重跑 `calls=4 / token 6,643 / 墙钟 18.0 s / trace 13 行`；
  单测 94 项过 —— `TestTracerAppend` 锁住"追加 vs 清空"，`TestWebSessionCost` 断言 `cost.source == "trace-file"`。
- **面试怎么讲**：*"这个 bug 最值得讲的是它**看起来完全正常**：报告照出、分数照算，只有一行数字是 0。
  我发现它是因为先给 CLI 路径做出了成本账，再拿 Web 路径对照，两边对不上。
  教训是：**同一个指标有多条入口时，必须交叉验证**，否则你以为自己有度量，其实只是有一条路径在默默返回 0。"*

## 10. 交付前自查清单（本项目固化下来的做法）

- 跑完全部单测 → 立刻看版本控制状态，确认没有随机命名的产物混进来
- 场景化的"事故复现"要留一个固定用例（例：无 Key 跑评测、上传图片版 PDF）
- 任何指标都要能指着产物文件说出处；测不出来的写"待人工"，不写形容词
- 真实简历跑出来的场次一律不进版本库（含简历片段）；测试用的场次与历史弱点库交付前清空/重置
- 改了模型/端点/参数，都要在输出里显式打印"当前生效的端点 + 模型链 + 关键参数"，让错配一眼可见
- **同一个指标有多条入口（CLI / Web / API）时，必须交叉验证数字**：只信一条路径，就会漏掉"某条路径默默返回 0"这类缺陷
- 汇总类指标要带 `source` 字段标明口径来源（进程内计数 vs 读产物文件），避免两个口径混着报
